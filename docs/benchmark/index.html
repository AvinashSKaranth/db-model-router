Methodology & fairness notes

  • All four contenders ran sequentially in separate Node processes, never concurrently; each applied the schema fresh (drop + create) and reseeded 2,000 identical rows from raw SQL before measuring.
  • Single-row scenarios (insert, read, update, upsert, delete, JSONB round-trip): 1,000 measured iterations × 5 runs. Bulk/tx scenarios: reduced iteration counts as labeled per scenario. Warmup excluded from timing.
  • Latency measured with performance.now() around each individual operation; p50/p95/p99 via nearest-rank percentile over all samples; throughput = total ops ÷ total sample time.
  • Everyone shares the same pg driver and a pool of max 10 connections.
  • db-model-router insert()/update()/upsert() re-SELECT the row after writing to return the full record (inside update the library also uses an UPSERT under the hood), and its find() has no LIMIT — the “filter + sort + limit 20” scenario uses list() for it. Measured as-is: this is the library's real cost.
  • Sequelize create()/upsert() do not re-SELECT. Validations enabled (parity with db-model-router's validation layer).
  • Prisma 7 uses the Rust-free client with @prisma/adapter-pg. createMany() does not return rows (idiomatic Prisma).
  • Drizzle has no validation layer (SQL-first thin ORM). price is passed as a string to match numeric semantics.
  • JSONB meta is written and read back in all contenders. Transaction scenarios wrap insert + update + audit-insert; the rollback scenario forces a throw and expects no partial writes.
  • Numbers are machine-specific — compare contenders against each other on the same machine, not against absolute targets.
